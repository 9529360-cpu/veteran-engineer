# Skill evaluation surfaces

Use these only when maintaining/evaluating Veteran Engineer. They are evidence surfaces, not runtime workflow owners.

- `evals.json` tests **behavior after the Skill is loaded**. Cases should pressure a reusable decision boundary and include counterexamples where ceremony should *not* trigger.
- `trigger_set.json` tests **whether the Skill should load at all**. Include obvious positives, obvious negatives, and near-miss negatives that share vocabulary without requiring substantial end-to-end engineering ownership.

Evaluation discipline:

1. Keep behavior and triggering verdicts separate. A Skill can route correctly once loaded but trigger too broadly or too narrowly.
   When the installed catalog has overlapping Skills, include nearest-alternative cases: prompts that should belong to the neighboring specialist as well as prompts where this Skill should remain the process/integration owner.
2. Compare candidate behavior against the prior Skill or a no-Skill baseline when a model runner is available.
3. For probabilistic trigger evaluation, run each query multiple times and inspect the trigger rate rather than trusting one sample.
4. Add a case for the exact reusable failure before or with the rule that fixes it.
5. When optimizing the trigger description, split both positive and negative queries into train and held-out test sets before the first optimization iteration. Preserve class balance, run each query multiple times when the runner supports it, and select the winning description from held-out performance rather than train performance. Do not inspect a failed holdout and copy its wording into the description; promote a new reusable boundary only after separate real-task evidence justifies it.
6. For behavior evolution, snapshot the prior Skill before a material change and compare candidate versus prior/no-Skill on the same prompts. If both versions pass an assertion easily, the case may not measure Skill value; harden or retire it instead of celebrating a meaningless green.
7. Keep some near-miss and cross-domain cases out of the immediate rule-writing loop when running model-level evaluations. Static repository tests may validate their schema, but maintenance changes should not be authored as literal answers to every held-out prompt.
8. Do not claim model-level improvement from schema/static tests alone. A fresh model/session must load the changed Skill to prove behavioral improvement.
9. Run **capability-delta ablation** for generic-looking additions when fresh runners exist. Compare the candidate against the prior/no-Skill baseline and keep the rule only if it improves a discriminating decision/evidence expectation enough to justify its context and workflow cost. If baseline and candidate both pass easily, narrow, harden, or remove the rule instead of treating a shared green result as Skill value.

10. Test material workflow rules across the capability/model tiers the Skill is expected to run on when runners are available. A step that only a stronger or higher-effort model volunteers is not yet a reliable workflow step; either make the instruction explicit enough to survive the weaker target or scope the Skill's support honestly.
11. Validate the evaluator before optimizing against it. Keep worker/session fixtures isolated, inspect a few raw transcripts and trigger traces, and sanity-check that repeated controls behave plausibly. Treat suspiciously uniform or topology-dependent scores as harness defects until disproven; never rewrite the Skill to fit a broken measurement pipeline.
12. Bind every model-level evaluation to the **exact loaded Skill identity**. Record the repository/source revision, packaged or installed content identity (hash/version/path), host/session generation, and whether the run started fresh after the edit. Repository edits, installed copies, and session-cached prompt bytes are different authorities. If you cannot prove the evaluated instance loaded the candidate bytes, classify the run as stale/unknown evidence rather than candidate behavior.
   Use `scripts/skill_identity.py <skill-root> --json` when a deterministic package/content hash helps bind source, installation, and evaluation records.

13. Record the **effective agent harness configuration** for live runs: agent/CLI name and version, model, reasoning/effort setting, base endpoint when non-default, harness version, sandbox/workspace mode, and Skill content hash. Treat an unpinned local default as part of the result metadata, not as an invisible constant.
14. Prefer fresh isolated workspaces and pre/post state capture for behavior cases that mutate repositories or external state. Grade deterministic state deltas before prose summaries so a pre-existing branch, file, commit, or provider resource cannot false-pass the candidate. Classify assertions the harness cannot observe as unavailable/skipped evidence rather than silently converting them to failure or success.
15. Keep **behavior failure** separate from **execution error**. A run is `failed` only when the agent/harness completed the case well enough for the declared assertions to be observed and at least one material assertion was false. A run is `errored` when the agent process, model endpoint, credential, sandbox, connector, evaluator, timeout, or harness failed before the task could be validly graded; exclude errored runs from Skill-improvement evidence and repair the execution environment first. If all candidate runs error, the Skill result is unknown, not bad.
16. Stage live evaluation by side-effect level. Run static/read-only and local-only cases before live-safe or external-effect cases; do not spend provider credentials or create remote effects merely to prove a routing rule that a cheaper case can falsify.
17. Put an explicit **evaluation budget** around probabilistic trigger/behavior optimization before scaling it: maximum iterations, runs per query, concurrent workers, wall-clock time, and provider/token spend when measurable. Start with a small serial control that includes obvious positives and negatives; only raise concurrency after the harness reproduces those controls. If a candidate suddenly reports near-zero positive recall, perfect negative precision, or a large topology-dependent swing, stop the optimization loop and debug the evaluator instead of spending more budget rewriting the Skill. Infrastructure errors, timeouts, and worker crashes must never be coerced into `did not trigger`.

18. Audit **task and grader validity** before optimizing the Skill against a score. Everything a deterministic grader requires should be inferable from the task/contract. Flag hidden requirements, implementation-specific assertions with valid alternatives, inadequate outcome coverage, contaminated fixtures, flaky infrastructure, and stale external rule sets. A broken or ambiguous eval is an eval defect, not evidence that the Skill needs another rule.
19. For non-deterministic agent behavior, use multiple trials when the runner permits it and keep outcome, transcript/process, and cost/stability metrics separate. Prefer deterministic state/output checks for objective facts, calibrated model/human rubrics for open-ended quality, and raw transcript inspection for suspicious changes. One aggregate score must not hide a critical invariant failure.
   Treat traces as diagnostic evidence by default, not a script the agent must imitate. Grade the delivered state/outcome first when multiple valid paths exist. Make a trajectory step a hard assertion only when it is itself a material process invariant such as authorization, destructive-action gating, required freshness, or an explicit design-before-production-mutation boundary; otherwise use tool/order traces to explain failures, cost, or suspicious behavior without rejecting a valid alternative path.
20. Require **environment equivalence** before interpreting candidate-versus-baseline score deltas as Skill capability. Record and match the execution variables that can change the task itself: CPU/RAM guarantees and ceilings, timeout policy, network/egress access, concurrency, dependency caches, sandbox/provider, and relevant service availability. Separate infrastructure errors from behavior failures. If the compared runs do not share an equivalent environment, report the result as confounded rather than treating a small score movement as Skill uplift or regression.
21. Treat eval suites as **freshness-sensitive signal**, not permanent truth. Re-audit or retire cases when the target models saturate them, when candidate and baseline both pass without discrimination, when public exposure creates contamination risk, when repository/runtime assumptions age out, or when repeated tuning has overfit the active prompt set. Preserve historical results for audit, but promote new Skill rules only from currently discriminating, valid, and appropriately held-out evidence.
22. For progressive-loading and router behavior, assert **negative loading** as well as positive reachability. A case should name the current owner that must load and the plausible future-stage or neighboring owners that must remain absent until their mechanism becomes active. Otherwise a routing suite can stay green while context tax, duplicated authority, and premature specialist loading quietly grow back.


## Benchmark interpretation

When repeated model runs are available, treat stability and efficiency as part of the evidence rather than looking only at one aggregate score:

- compare candidate, prior-Skill, and no-Skill baselines on the same scenario set under equivalent execution resources and timeout/network policy;
- record run pass rate plus score mean and standard deviation; high variance is an instability/flakiness signal, not a hidden improvement;
- record duration and token use when the runner exposes them, and require a meaningful behavior/quality gain before accepting a large cost increase;
- flag assertions or rubric rows that pass equally under candidate and baseline as non-discriminating, then harden or retire them;
- inspect outliers and raw transcripts before changing instructions to fit a number;
- after a short tuning loop, expand or refresh the test set instead of repeatedly optimizing the same prompts; retire or quarantine saturated/contaminated cases instead of preserving them as ceremonial greens.

Use `scripts/benchmark_score.py run-1.json run-2.json ... --json` to aggregate repeated structured benchmark runs. `--max-stddev` may be used as an explicit stability gate for a controlled comparison; do not invent a universal variance threshold.


## Qualitative output review

Do not turn subjective product/design quality into arbitrary assertions merely to make the benchmark numeric. When fresh model runners can produce comparable artifacts:

- preserve the real output artifacts needed to judge the task, including rendered screenshots/recordings and interaction evidence for UI work rather than only the assistant summary;
- compare candidate versus prior/no-Skill output side by side, preferably blinded as A/B when version identity could bias the reviewer;
- keep objective checks (missing states, overflow, keyboard behavior, build/test results, authorization behavior) separate from qualitative judgments such as hierarchy, product fit, restraint, and visual direction;
- record why one output is better, not only which one won, so the next Skill edit targets a reusable mechanism instead of the winning surface style;
- treat human/independent qualitative review as complementary evidence, not permission to ignore deterministic failures or critical red flags.

If the environment cannot run the candidate Skill on a fresh model instance or cannot render the relevant product surface, do not fabricate a qualitative comparison; keep the evidence level at static/structural validation.
23. For mixed-signal engineering cases, grade **primary-owner selection and deferral**, not just reference reachability. The agent should keep current domain/risk constraints active, queue genuinely different-stage owners, and avoid deferring the failing mechanism during incident or diagnostic work. Include at least one case where an explicit stage-advance signal moves an accepted upstream contract into implementation.
24. For multi-stage handoff cases, grade **owner-transition legality**, not merely whether the next specialist is relevant. Require fresh generation/owner/authority identity, explicit exit proof bound to that authority, no skipped queued intermediate owner, and a new downstream authority identity. Grade backward movement as invalidation/reopen rather than ordinary handoff, and reject completion while requested future-stage owners remain queued. Static transition gates prove metadata discipline only; use model/runtime evals to judge whether the chosen exit evidence actually closes the semantic contract.
25. For proof-triggered owner transitions, grade **decision genealogy**, not just current state. Accepted transitions should emit an immutable receipt bound to the exact proof/authority/ledger head; invalidation should append supersession rather than rewrite history; resume should block when owner-state and ledger projections disagree. Keep semantic correctness in model/repository/runtime evidence rather than treating hash validity as proof that the engineering decision was right.
26. For clause/decision provenance cases, grade **affected-set precision**, not just whether invalidation happened. Semantic dependency edges may propagate invalidation; observational links must not. A preserved node may prune its downstream branch only when fresh proof bound to the current authority explicitly supports that preservation. When provenance is absent, the conservative owner-lineage fallback is acceptable; when provenance exists, blanket downstream invalidation is a regression.
27. For incremental repair cases, grade **recompute versus revalidate versus reuse**. A stale root should be recomputed or replaced first; semantic dependents should be revalidated in dependency order rather than immediately rewritten; unrelated branches should remain reusable. If an exact replacement produces the same semantic decision hash, downstream work should be change-pruned without ceremonial revalidation. Do not treat hash equivalence as evidence for unrelated decisions or use it to bypass a genuinely changed semantic dependency.
28. For provenance-driven parallel repair, grade **dependency parallelism separately from execution parallelism**. Independent decision branches are only candidate siblings. Before fan-out, require repository-derived write sets, risk classes, and validation oracles, then let the mission work graph serialize write/resource conflicts. A dependency DAG alone must never authorize concurrent mutation.
