Use this only when deliberately maintaining or evolving Veteran Engineer. It records reusable mechanisms learned from mature Agent Skills ecosystems so future edits can synthesize evidence instead of copying platform-specific prose.

## Source selection rule

Prefer mechanisms that change agent behavior across repositories. Keep platform-specific loader limits, metadata syntax, tool names, permission models, and UI commands in host adapters or maintenance notes unless the core Skill truly depends on them.

For each source ask:

`source authority -> reusable mechanism -> host-specific constraint -> adoption owner -> regression proof`

Do not promote a rule because a popular repository uses it. Promote it when the mechanism addresses an observed reusable failure and survives counterexamples.

## Adoption discipline

Before importing a new mechanism:

1. Name the concrete failure or uncertainty it addresses.
2. Check whether an existing owner can express it by replacement, narrowing, moving, or deletion before adding a new section/file.
3. Separate universal mechanism from host syntax/tooling.
4. Add or refresh the smallest behavior/trigger/structural regression that would catch the old failure.
5. Re-run the relevant regression set and package validator.
6. Record material source additions here only when they remain useful for future maintenance.

When two mature sources disagree, do not average them. Resolve the disagreement from the active host contract, user outcome, repository evidence, and the specific failure being prevented.
